Test summary and scope 测试摘要与范围

This benchmark compares sixteen C++, Rust and Python implementations, including serial references, on float64 matrix–vector multiplication. The workloads are dense GEMV, uniform CSR SpMV and skewed CSR SpMV. Measurements separate warm-call latency, startup costs, sustained throughput and process-tree memory. The objective is to select an execution and scheduling strategy for each workload. 本次测试对比 C++、Rust 与 Python 的十六种矩阵向量乘法实现，包含串行参考。数据类型统一为 float64，负载分为稠密 GEMV、均匀 CSR SpMV 和不均匀 CSR SpMV。分别测量热调用耗时、启动成本、持续吞吐与进程树内存，用于评估不同负载下的执行方式与调度方案。

Selection summary. For standard matrix operations in Python, use NumPy/SciPy as the initial implementation. For a new native implementation covering this study's three large workloads, prioritize oneTBB: it records the lowest warm-call median in all three 16-worker stress cases. For regular loops in an existing C++ project, start with OpenMP; for Rust, use Rayon. The selection criteria distinguish measured performance from integration-cost recommendations. 选型摘要。Python 标准矩阵运算优先采用 NumPy/SciPy。针对本文三种大矩阵负载新增原生实现时，优先评估 oneTBB：本轮三项 16 路压测中，它的热调用中位数均最低。已有 C++ 项目的规则循环先采用 OpenMP，Rust 项目采用 Rayon。具体选型依据区分实测性能与接入成本。

A worker is a participating thread or process. The configured p specifies requested parallelism or a runtime limit; active concurrency is not sampled. The comparison concerns concrete implementations, not languages in isolation: Python scalar loops, BLAS calls and Numba-compiled loops use different execution paths. worker 指参与计算的线程或进程。配置中的 p 表示请求的并行度或运行时上限，本实验未采样瞬时活跃线程数。比较对象是具体实现，而非孤立的语言特性：Python 标量循环、BLAS 调用与 Numba 编译循环采用不同的执行路径。

The scope is CPU matrix–vector multiplication. Matrix–matrix multiplication, GPU execution, distributed systems and I/O concurrency are excluded. Dense storage does not imply a compute-bound workload; GEMV's arithmetic intensity is analyzed below. 测试范围限定为 CPU 矩阵向量乘法，不包含矩阵矩阵乘法、GPU、分布式系统或 I/O 并发。稠密存储不等于计算密集型负载；后文会分析 GEMV 的算术强度。

Measurement condition: CPU contention. During this run, another job occupied the same four P-cores and several additional CPU-heavy tasks were active. The baseline host load average was about 9.5 at the start and 10.8 at the end. CPU affinity sets where a program may run; it does not reserve those cores. This experiment records behavior on a busy workstation, not clean-machine peak performance. Close rankings and scaling ratios need a repeat on an idle host.测量条件：存在 CPU 竞争。运行期间，另一个任务占用了相同的四个 P 核，同时还有多个高 CPU 负载任务。基础测试开始与结束时，主机一分钟平均负载约为 9.5 和 10.8。CPU 亲和性只限定程序可以在哪里执行，不会独占这些核心。本轮记录的是繁忙工作站上的表现，不能当作空闲机器的峰值性能；接近的名次与扩展比需要在空闲环境复测。

Operation contract and input construction 运算约定与输入构造

Every call reads an already constructed matrix and vector, computes in float64, and writes every element of the output. Rows are independent, so workers may own different output ranges without a shared accumulator. The call ends only after all workers finish. This is the GEMV operation with a unit multiplier and no previous-output contribution. 每次调用读取已经构造好的矩阵与向量，以 float64 计算，并写完输出的每一个元素。各行互相独立，可以把不同输出区间交给不同 worker，无需共同更新一个累加器。所有 worker 完成后，这次调用才算结束。对应 GEMV 的定义，这里乘法系数为一，不累加原来的输出。

Both sparse inputs average 64 stored entries per row. Values and vector elements come from deterministic formulas; the sparse inputs select columns from that formula and leave all other positions absent. Thus implementations of one workload share the same mathematical input, while dense and sparse workloads are different matrices. About one percent of stored values are explicit zeros, retained in every implementation. As in SciPy’s CSR definition, the reported nnz counts stored entries, including those zeros. 两种稀疏输入都平均每行存储 64 项。数值和向量元素由确定的公式生成；稀疏输入从这个公式中选择一部分列，其余位置不存储。因此，同一工作负载的各个实现使用相同的数学输入，稠密与稀疏负载之间则是不同的矩阵。约百分之一的存储值恰好为零，各实现都保留它们。与 SciPy 的 CSR 定义一致，结果中的 nnz 统计存储项，也包含这些显式零。

Input formulas and exact validation输入公式与精确校验

The third expression gives the column of sparse entry k in row i. The chosen column counts keep these columns distinct within a row. Power-of-two denominators make every product, and every row sum at these sizes, exactly representable. An independent Python oracle uses only integer numerators to derive each scaled output q = 1024*y[i], its signed sum, and an order-sensitive 64-bit value hash. A correct checksum alone could hide swapped or cancelling errors; the hash adds a second check, though it is not a proof against every possible collision. 第三式给出稀疏矩阵第 i 行第 k 个存储项的列下标；选定的列数保证同一行内没有重复列。分母都是二的幂，因此在本次尺寸下，乘积和每行累加结果都能被精确表示。独立的 Python 参考程序只计算整数分子，得到各行放大后的 q = 1024*y[i]、它们的有符号总和，以及对顺序敏感的 64 位逐值哈希。只核对总和，可能漏掉交换行或相互抵消的错误；哈希提供第二层核对，但不等于排除了所有可能的碰撞。

The baseline checks the whole output after each call, outside the kernel timer. The sustained-load experiment checks the first and last outputs, avoiding a full validation scan between iterations. Both are compared with the independent oracle before a record is accepted. 基线实验在每次调用后核对完整输出，校验不计入内核时间。持续负载实验核对首次和最终输出，避免每两次迭代之间插入完整扫描。两种实验都要与独立参考值一致，记录才会被接受。

Environment and measurement protocol 测试环境与测量协议

The baseline uses one, two and four workers on four physical P-cores of an Intel Core i7-1270P, with logical CPU IDs 0, 2, 4 and 6. The monitor runs on E-cores; those cores are not reserved. The processor itself has four P-cores, eight E-cores and sixteen hardware threads; the baseline deliberately does not treat all sixteen as identical cores. Each worker count may use the same four-core CPU set, rather than being restricted to its own smaller set. 基线使用 Intel Core i7-1270P 的四个物理 P 核，逻辑 CPU 编号为 0、2、4、6，分别运行一、二、四个 worker；监测进程放在 E 核上，但不独占这些核心。这颗处理器实际包含四个 P 核、八个 E 核，共十六个硬件线程，基线不把它们视为十六个相同性能的核心。不同 worker 数量都可使用同一个四核 CPU 集合，而不是各自再绑定到更小的集合。

Each configuration runs in three fresh processes. A process performs its first call, then five repeated calls; the figures summarize those fifteen warm samples with a median and interquartile range. Calls within one process share runtime state and are correlated. The interval describes observed variation, not a confidence interval from fifteen independent experiments. Configurations are shuffled with a fixed seed and run one at a time. 每个配置启动三个新进程，每个进程先运行首次调用，再重复五次。图中用这十五个预热后样本的中位数与四分位区间呈现表现。同一进程内的调用共享运行时状态，样本之间有关联；这个区间描述观察到的波动，不是十五次独立实验推导出的置信区间。配置顺序按固定随机种子打乱，逐个运行。

Dense GEMV: execution paths and scaling 稠密 GEMV：执行路径与扩展性

Each dense matrix element is read for one multiply and one accumulation. If the vector stays reusable in cache and the matrix is read once, a large float64 GEMV performs roughly two floating-point operations for every eight matrix bytes. This gives a best-case traffic estimate near 0.25 FLOP per byte, before extra transfers or cache misses. GEMM can reuse matrix tiles across many output columns; this experiment cannot. The distinction follows the usual arithmetic-intensity analysis, but it does not by itself prove that any particular measured implementation reached the CPU’s memory-bandwidth limit. 每读取一个稠密矩阵元素，执行一次乘法和一次累加。假定向量可以在缓存中复用、矩阵只读取一次，较大的 float64 GEMV 每读取八字节矩阵数据，大约只做两次浮点运算。理想的数据搬运口径下，算术强度接近每字节 0.25 FLOP，该估计未计入额外传输与缓存未命中。GEMM 可以让矩阵分块在多列输出之间复用，本次 GEMV 不具备这种跨输出列的复用。这与常见的算术强度分析一致，但仅凭这个推导，还不能证明某个实测实现已经达到 CPU 的内存带宽上限。

The largest observed separation is between scalar Python and native numerical kernels: scalar Python takes 384.19 ms, its four-thread version 377.77 ms, and one-thread NumPy 2.05 ms. The two Python-loop distributions overlap; these data show no clear thread-pool gain for that loop. NumPy moves the numerical work into a compiled BLAS kernel, so its much shorter time cannot be attributed to a better Python loop scheduler.最大的实测组间差距出现在 Python 标量循环与本地数值内核之间：Python 标量循环为 384.19 ms，四线程版本为 377.77 ms，而单线程 NumPy 为 2.05 ms。前两者的分布重叠，数据没有显示这个循环在线程池中获得明确提升。NumPy 把数值工作交给编译后的 BLAS 内核，较短耗时不能解释成“更好的 Python 循环调度器”。

A small scaling sample makes the machine constraint visible. These are the same backend at each worker count, with the input unchanged. Several native paths fail to improve as workers increase on the occupied P-cores. This is an observation about this run; an idle-machine test is needed before blaming the library or claiming a bandwidth ceiling.下面从完整数据中选取几种后端，保持输入不变，比较同一后端的 worker 数量。在已经被占用的 P 核上，多个本地执行路径没有随 worker 增多而改善。这描述的是本轮现象；归因到某个库，或断言达到带宽上限，都需要空闲环境的进一步测量。

The NumPy row is an ecosystem comparison: it calls an optimized BLAS kernel, while the C++, Rust and Numba paths use explicit row loops. Its difference includes kernel engineering, compiler decisions and SIMD, not just a thread scheduler. BLAS is limited to one thread even inside the Python thread pool, to control nested parallelism. CSR SpMV: row distribution and scheduling CSR SpMV：行分布与调度开销

CSR stores values, column indices and row boundaries. A worker visits only stored entries, but must use each column index to find the corresponding vector element. Equal-row partitioning distributes stored entries evenly when row lengths are uniform. In the skewed input, however, the first 6.25% of rows contain 76.56% of all stored entries. CSR 保存数值、列下标和每行的边界。worker 只遍历存储项，但还要通过列下标找到对应的向量元素。行长一致时，均分行数可以均分存储项；本次长行集中分布时，均分行数会造成存储项分配不均。本次不均匀输入中，前 6.25% 的行包含全部存储项的 76.56%。

The four-process shared-memory path takes 126.84 ms for uniform rows and 249.91 ms for skewed rows, a 1.97× ratio. With equal contiguous quarters, the first worker receives 81.25% of stored entries in the skewed case. Three more workers cannot divide that worker’s already assigned slab. The changed column access and host contention also affect the measured ratio.四进程共享内存路径在均匀行上为 126.84 ms，在不均匀行上为 249.91 ms，后者约为前者的 1.97 倍。连续四等分时，不均匀输入中的第一个 worker 分到了 81.25% 的存储项；其他三个 worker 无法再拆分它已领取的行块。列访问变化与主机竞争也会影响这个实测比值。

The result does not establish that dynamic scheduling always has lower latency: on the skewed matrix, OpenMP static measures 2.44 ms and dynamic measures 3.79 ms here. The controlled input gives a reason to investigate load balance; this busy-host measurement does not isolate its contribution from scheduling cost and memory access.结果也没有证明动态调度总是更快：本轮不均匀矩阵上，OpenMP static 为 2.44 ms，dynamic 为 3.79 ms。这个输入提供了研究负载均衡的理由，但繁忙主机上的测量并未把它与调度成本、访存等因素分离。

OpenMP’s dynamic variant hands out chunks of 32 rows as workers become available. oneTBB’s task scheduler and Rayon’s work stealing also let idle workers take remaining tasks. These mechanisms can reduce a long tail, but scheduling more chunks costs something. One fixed chunk size is a tested choice, not the optimum for every matrix. OpenMP 的 dynamic 版本让空闲 worker 按 32 行一组领取任务。oneTBB 的任务调度器和 Rayon 的工作窃取也让空闲 worker 有机会接手剩余任务。这些机制可以缩短拖尾，但调度更多分块本身也有成本。这里的固定分块大小是一个被测选择，不是所有矩阵的最优值。

The standard-thread and executor paths deliberately use equal contiguous row slabs. Numba’s default prange schedule also divides iterations approximately evenly. They could be redesigned to partition by cumulative stored entries instead. The comparison therefore evaluates the supplied implementations, not an inherent inability of those APIs to balance sparse work. Uniform and skewed matrices also change column-access patterns, so their difference is not a pure measurement of scheduling alone. 标准线程与 executor 路径在本次实现中采用连续行均分；Numba 的 prange 默认调度同样近似均分迭代。它们都可以改成按累计存储项数划分工作。因此，这里比较的是给出的实现，不代表这些 API 天生无法均衡稀疏工作。均匀与不均匀矩阵的列访问模式也发生了变化，两者之差不能视为纯粹的调度成本。

Sustained-load test: throughput and latency distribution 持续负载测试：吞吐与延迟分布

The sustained-load profile measures throughput and the per-call latency distribution on larger inputs. It increases dense dimensions to 4,096 × 4,096 and sparse input to 131,072 × 131,072, still averaging 64 entries per row. It runs the eleven parallel implementations with sixteen workers on all sixteen logical CPUs. Each timed process repeats work for at least ten seconds after its first call; a separate ten-second pass measures memory. 持续负载配置用于测量更大输入下的吞吐量与逐次调用延迟分布。稠密输入扩大到 4,096 × 4,096，稀疏输入扩大到 131,072 × 131,072，仍平均每行 64 项。十一种并行实现均使用十六个 worker，可运行在全部十六个逻辑 CPU 上。每个计时进程在首次调用后连续重复至少十秒，内存再用另一轮十秒实验测量。

The two process-pool variants differ in data-transfer and buffer-ownership costs. With ProcessPoolExecutor, the copy path serializes a row slab and a copy of x for each task, then returns output bytes. Engineering conclusions and library selection 工程结论与库选型

For a new native implementation covering these three large workloads, prioritize C++ oneTBB. Among the eleven parallel implementations in the 16-worker stress test, it records the lowest warm-call median in all three cases: 11.82 ms for dense, 8.87 ms for uniform CSR, and 9.30 ms for skewed CSR. Its sampled lifecycle peak PSS is about 130 MiB for dense and 101 MiB for either sparse input, close to OpenMP's 129 and 100 MiB. 针对本文三种大矩阵负载新增原生并行实现时，优先采用 C++ oneTBB。在 16 路压测的十一种并行实现中，它的热调用中位数均最低：稠密 11.82 ms，均匀 CSR 8.87 ms，不均匀 CSR 9.30 ms。生命周期 PSS 采样峰值约为稠密 130 MiB、两种稀疏各 101 MiB，与 OpenMP 的 129 和 100 MiB 接近。

On skewed CSR, oneTBB takes 9.30 ms versus OpenMP static's 20.91 ms, a measured speedup of about 2.25×. On dense input, oneTBB's 11.82 ms is only about 1.2% below OpenMP dynamic's 11.97 ms. That small difference is insufficient evidence for migrating an existing implementation. Each stress result comes from one timed window on a contended host, and serial NumPy/SciPy was excluded from this larger test. The recommendation is limited to the tested workload mix and must be validated on the target machine. 不均匀 CSR 上，oneTBB 为 9.30 ms，OpenMP static 为 20.91 ms，实测加速比约为 2.25。稠密输入上，oneTBB 的 11.82 ms 仅比 OpenMP dynamic 的 11.97 ms 低约 1.2%，不足以据此迁移已有实现。每项压测只有一个计时窗口，主机存在 CPU 竞争，且该规模未测试串行 NumPy/SciPy。推荐范围限于已测负载组合，落地前需要在目标机器上复验。

  1. Improve the numerical kernel before adding workers. On the baseline dense input, the Python scalar loop takes 384.19 ms, its four-thread version 377.77 ms, and single-thread NumPy 2.05 ms.   2. Plan data reuse before creating a process pool. This removes repeated bulk transfers in this implementation; interpreter and coordination costs still remain. 使用多进程前，先安排数据如何复用。同样的稠密输入、四个进程，复制版测得 329.16 ms、236.0 MiB 的 PSS 采样峰值，共享版为 192.32 ms、89.6 MiB。反复处理大型只读数组时，可以先挂接缓冲区，随后只发送行范围，并让各进程负责互不重叠的输出。这消除了本实现中反复的大块传输，解释器与协调成本仍然存在。

For a one-shot command, measure launch to exit; for repeated work, account for how many calls share initialization and compilation costs. Repeated short operations also deserve a comparison between a reusable pool and per-call thread creation.   5. Tune worker count against available CPU capacity. Dense OpenMP static goes from 3.83 ms with one worker to 4.02 ms with four; Rayon goes from 4.24 to 4.70 ms. Implementation details and reproduction 实现细节与复现方法

For ordinary GIL-enabled CPython, threads running Python scalar loops cannot execute that Python work simultaneously across cores. That constraint is described in the threading documentation. It does not imply that every Python thread pool is CPU-serial: many NumPy operations release the GIL, and SciPy also exposes native numerical work. Here arrays are read-only inputs and workers write disjoint output ranges; CSR objects are not modified during computation. 普通的、启用 GIL 的 CPython 中，多个线程无法把这些 Python 标量循环同时放到不同核心上执行，threading 文档说明了这个约束。但这不意味着所有 Python 线程池都只能串行算：不少 NumPy 操作会释放 GIL，SciPy 也提供本地数值内核。本次输入数组只读，各 worker 写入互不重叠的输出区间，计算期间不修改 CSR 对象。

            total += values[k] * x[indices[k]]
        output[row] = total

Numba uses its OpenMP threading layer in this experiment. Its Python loop is compiled to native code and scheduled through OpenMP; the Numba and C++ OpenMP paths therefore share a runtime family. The threading-layer documentation also distinguishes setting the pool’s maximum size with NUMBA_NUM_THREADS from masking existing threads with set_num_threads. The harness sets the former before importing Numba, so a small worker count does not retain a deliberately oversized pool. 本次 Numba 使用 OpenMP 线程层，Python 循环编译为本地代码后由 OpenMP 调度，因此 Numba 与 C++ OpenMP 路径使用同一类运行时。线程层文档还区分了用 NUMBA_NUM_THREADS 设置池的最大规模，与用 set_num_threads 屏蔽已有线程。运行器在导入 Numba 前设置前者，避免小 worker 配置仍有意保留一个过大的池。
