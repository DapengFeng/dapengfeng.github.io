Unified memory gives the CPU and GPU access to a common memory pool. It removes a separate small VRAM capacity barrier, but does not turn the entire installed RAM into freely allocatable model memory. The operating system, driver limits, other applications and inference buffers still matter. Likewise, Spark’s “up to 1 PFLOP FP4” is a theoretical FP4 peak using sparsity; it is not a measured chat speed and cannot be divided by an Apple TOPS figure to choose a winner. NVIDIA’s datasheet footnote specifies the sparse FP4 basis.统一内存让 CPU 与 GPU 访问共同的内存池，消除了独立显存容量较小这一类限制，但整机内存并不会全部变成模型可自由使用的空间。操作系统、驱动分配限制、其他应用和推理缓冲仍要占位置。同理，Spark“最高 1 PFLOP FP4”是采用稀疏性的理论 FP4 峰值，不是聊天实测速率，也不能拿它与 Apple 的 TOPS 相除来决定输赢。NVIDIA 规格书脚注明确了稀疏 FP4 口径。

Size the whole working set内存要算整个工作集

Start with raw weight storage. P is the number of stored parameters, and q is the number of bits per parameter. At exactly four bits, 8B needs 4 GB, 32B needs 16 GB and 70B needs 35 GB before scales, unquantized tensors and runtime allocations. A “4-bit model” file is not guaranteed to equal that arithmetic minimum.先算权重的原始存储量。P 是需要存储的参数数目，q 是每个参数的位数。按严格 4 bit 计算，8B 为 4 GB，32B 为 16 GB，70B 为 35 GB；这里还没放入量化缩放因子、保留高精度的张量与运行时分配。“4 bit 模型”文件不一定恰好等于这个算术最小值。

The second large allocation is the KV cache: each attention layer retains keys and values for tokens already processed. For a conventional full-context decoder with equal-length sequences, its uncompressed size is approximately the expression below. L is the layer count, Hkv the number of key/value heads, d the head dimension, T the cached tokens per sequence, B the number of resident sequences and s the bytes per element. T includes the prompt and generated tokens retained so far.另一项大分配是 KV cache：注意力层保存已经处理过的 token 的键和值。对于常规全上下文解码器，若各路序列等长，未压缩 KV 的大小可按下式估算。L 是层数，Hkv 是键／值头数，d 是头维度，T 是每路缓存的 token 数，B 是驻留序列数，s 是每个元素的字节数。T 包含仍被保留的输入与已生成内容。

Grouped-query attention reduces Hkv; sliding windows, shared prefixes and compressed caches change this budget. Quantizing the weights does not automatically quantize the KV cache. Transformers’ cache documentation describes the separate cache strategies and their trade-offs.分组查询注意力会减少 Hkv；滑动窗口、共享前缀和压缩缓存会改变预算。权重量化不等于 KV 也被量化。Transformers 的缓存文档分别说明了这些策略及其取舍。

Use one explicit example: a dense 70B model, four-bit raw weights, 80 layers, 8 KV heads, head dimension 128 and FP16 KV elements. Assume quantization metadata adds 10% to raw weights, and reserve 16 GiB for the OS, applications and runtime. These last two numbers are planning assumptions, not measurements or universal overhead ratios. The KV allocation is 320 KiB per cached token per sequence.用一个参数明确的算例：70B 稠密模型、4 bit 原始权重、80 层、8 个 KV 头、头维度 128，KV 元素采用 FP16。再假定量化元数据增加原始权重的 10%，为系统、应用与运行时预留 16 GiB。后两项是规划假设，不是实测，也不是通用开销比例。这个结构每路序列的每个缓存 token 需要 320 KiB。

This is why 96 GB can be sensible for a bounded single-user workload and still be a poor choice for four long conversations. Check the actual checkpoint’s loaded memory, prefill peak and the platform’s allocation limit. For the single-sequence 70B Q4 / 32K case, I would first validate the 96 GB Mac. Consider 256 GB for multiple resident models, four long conversations, or measured peaks approaching the allocation limit. Spend on memory when that is the constraint; extra SSD space and swap do not remove it. On Spark, reduce context/concurrency or change model format when the 128 GB envelope is insufficient.因此，96 GB 可以适合边界明确的单用户任务，却不一定适合四路长对话。 需要核对具体权重的加载占用、预填充峰值与平台的分配上限。对于单路 70B Q4／32K 任务，我会先验证 Mac 的 96 GB 档位。需要多模型同时驻留、四路长对话，或实测峰值逼近分配上限时，再考虑 256 GB。内存确实成为约束时再为它花钱；增加 SSD 或交换空间解决不了同一问题。Spark 的 128 GB 不够时，需要缩短上下文、降低并发，或更换模型格式。

For a mixture-of-experts model, distinguish active parameters per token from total stored parameters. A 235B model with only a small subset active still has about 117.5 GB of raw four-bit weights if all experts stay resident. That is already too close to a 128 GB system for a casual “it fits” claim. Streaming experts from storage can change capacity requirements, but also changes latency and the deployment problem.对于混合专家模型（MoE），要区分每个 token 的激活参数与全部存储参数。235B 模型即使每次只激活一小部分专家，全部专家驻留时，4 bit 原始权重仍约为 117.5 GB。对 128 GB 整机而言，这已经不能轻率地说“装得下”。从存储中按需调入专家可以改变容量需求，但也改变了延迟与部署问题。

Separate first-token latency from generation speed首字等待与逐字生成是两种负载

An autoregressive model first processes the prompt (prefill), then produces new tokens one step at a time (decode). A long document can take time before the first visible answer even if subsequent tokens arrive quickly. Conversely, a short prompt can start quickly and then crawl. Measure time to first token, inter-token latency and aggregate output throughput separately; include queueing when testing a service.自回归模型先处理输入（prefill，预填充），再逐步生成新 token（decode，解码）。长文档可能让首字等待很久，即使后续输出很快；短问题也可能很快开始，之后却一个字一个字地挪。首 token 延迟、相邻 token 延迟与总输出吞吐要分开测，服务验收还要把排队时间算进去。

Prefill can reuse weights across many prompt tokens and exploit large matrix operations. Single-sequence dense decode often has much less reuse: it streams a large fraction of the weights to produce one token. This makes memory bandwidth a useful first constraint. Long contexts add KV traffic, while batching changes the reuse pattern. NVIDIA’s attention analysis explains why prefill and decode need different attention designs.预填充能在多个输入 token 之间复用权重，利用较大的矩阵运算。单路稠密模型解码的复用机会通常小得多：为了产生一个 token，需要读取大量权重。因此，内存带宽是一个有用的初始约束。长上下文还会增加 KV 读取，并批处理则改变复用方式。NVIDIA 对注意力的分析说明了为什么两个阶段需要不同的优化。

For the narrow model in which every decode step reads all 35 GB of raw weights once, advertised bandwidth gives 273 / 35 = 7.8 and 1,200 / 35 ≈ 34.3 token/s. These are ideal weight-streaming ceilings within those assumptions. They omit quantization metadata, dequantization, attention/KV traffic, synchronization and other memory users. They are not measured speeds, expected speeds or a universal bound on all inference algorithms.如果严格假定每个解码步都完整读取一次 35 GB 原始权重，代入标称带宽，得到 273／35 = 7.8，以及 1,200／35 ≈ 34.3 token/s。这是在上述假设内的理想权重读取上界，省略了量化元数据、反量化、注意力与 KV 读取、同步以及其他内存使用者。它们不是实测速率、预期速率，也不是所有推理算法的普遍上界。

For a person reading one answer, per-user latency usually matters most. For four agents or users, a serving engine can batch their work and raise total throughput while making each individual stream slower. A well-supported CUDA kernel can also change prefill performance dramatically. Therefore my Mac recommendation is for a compatible personal inference workload, not a benchmark verdict over every model and serving configuration.一个人阅读一个回答时，更关心自己的延迟。四个 agent 或用户同时访问时，服务引擎可以并批提高总吞吐，但每一路未必更快；适配良好的 CUDA 内核也可能显著改变预填充性能。因此，前文推荐 Mac 的前提是适配的个人推理任务，并不是所有模型与服务配置的跑分裁决。

For remote use from your own laptop, an SSH tunnel keeps the service off the public network, for example ssh -L 8000:127.0.0.1:8000 user@spark-host.推理模型可能在最终回答前消耗输出 token，因此健康检查成功不代表较短的输出预算一定能完成回答。兼容 OpenAI 的 API 可以让编辑器或聊天界面改用本地 base URL，但工具调用、推理字段与多模态输入并不会因此在所有模型上完全一致，需要验证具体客户端流程。如果从自己的笔记本远程使用，可以通过 SSH 隧道访问，例如 ssh -L 8000:127.0.0.1:8000 user@spark-host，不必把服务端口开放到公网。

Make the application local, not only the model模型在本地，应用链路也要在本地

  1. Question问题输入The local client submits a question about your documents.本地客户端提交与文档有关的问题。
  2. Retrieval检索上下文A local embedding model and index select relevant passages.本地嵌入模型与索引选出相关片段。
  3. Generation生成回答The inference API uses the question and passages to generate an answer.推理 API 结合问题和片段生成回答。

For a private document assistant, begin with retrieval-augmented generation (RAG): parse and index local documents, retrieve relevant passages, and pass only those passages to the model with source references. Keep embeddings, reranking and the vector index local as well. A local language model attached to a cloud embedding API or an unrestricted web tool is not an offline application. Download models and dependencies first, then test the workflow with network access disabled.私人文档助手可以先从检索增强生成（RAG）开始：解析并索引本地文档，检索相关片段，把这些片段及其出处交给模型。嵌入、重排序与向量索引也要留在本地。模型在本机，但嵌入调用云端 API、工具可以随意联网，这仍不是离线应用。先下载模型和依赖，再断网测试完整流程。

Use adapter fine-tuning when the goal is a repeatable style, output format or task behavior; use retrieval for documents that change and must be cited. Both MLX-LM and the NVIDIA ecosystem offer supported adapter-training routes. CUDA dependence makes Spark the more natural development choice, but Mac is not “inference only.” Conversely, a vendor’s “fine-tune 70B” statement must not be read as full-parameter Adam training of a 70B model. Gradients, optimizer states and activations can dwarf quantized inference memory.需要稳定的文风、输出格式或任务行为时，可以考虑适配器微调；文档会更新、回答需要出处时，优先使用检索。MLX-LM 与 NVIDIA 生态都有受支持的适配器训练路线。依赖 CUDA 的项目更适合以 Spark 起步，但 Mac 并非“只能推理”。反过来，厂商所说“可微调 70B”，也不能理解为能用 Adam 完整训练 70B 的全部参数：梯度、优化器状态和激活量可能远大于量化推理的内存。

Multi-machine execution is a separate engineering project on either platform. ConnectX networking on Spark and supported Thunderbolt/RDMA workflows on Mac can connect devices, but a cable does not turn two computers into one transparent memory pool. The runtime must partition work, communicate tensors and tolerate the added latency. Validate a single node first, then justify a cluster with a workload that needs it.两种平台的多机运行都属于另一项工程。Spark 的 ConnectX 网络与 Mac 上受支持的雷雳／RDMA 工作流可以连接设备，但插上电缆，不会把两台电脑变成一个透明的大内存池。运行时需要切分任务、交换张量，并承担额外延迟。先验证单机，再用实际任务证明集群的必要性。

There are two useful comparisons. For a controlled hardware/backend comparison, use the same GGUF file, llama.cpp revision, context, KV type and GPU offload policy, with CUDA on Spark and Metal on Mac. For the system you would actually use, test each platform’s best supported stack with comparable model quality and the same task set. Label the two comparisons separately; forcing one common backend can hide native advantages, while unmatched native quantizations can change answer quality.有两种有价值的比较。第一种是控制变量：使用相同 GGUF、llama.cpp 版本、上下文、KV 类型与 GPU 卸载策略，Spark 用 CUDA，Mac 用 Metal。第二种是比较实际要用的系统：各自采用适配良好的软件栈，控制模型质量，跑同一组任务。两种结果分别标注；强制同一后端可能掩盖原生优势，不同原生量化又可能改变回答质量。

Total cost is the configured machine, tax and warranty, storage/backup, electricity and maintenance time. SSD space holds checkpoints; it does not replace inference memory or memory bandwidth.
